## NEW findings from the fold (fresh-eyes pass on the changed surfaces)

1. BLOCKING — the pipeline writer prompt never instructs the verdict tail,
   but the flow now REQUIRES it. pipeline.mjs:298 gates progress on
   `writerResult.verdict === 'APPROVED' | 'APPROVED_WITH_NOTES'`, yet the
   writer prompt (pipeline.mjs:260-266) — unlike the reviewer
   (pipeline.mjs:330) and merger (pipeline.mjs:346) prompts, and unlike the
   loop command's generic prompt (loop.mjs:360) which instructs the tail for
   EVERY role — contains no "End with exactly: VERDICT: …" contract. A real
   writer on either platform has no reason to emit a verdict, parseVerdict
   returns BLOCKED-unparseable, every attempt consumes a gate iteration, and
   every subtask escalates at the cap: `baton pipeline run` cannot complete
   any subtask with real children. Masked in tests because every fake runner
   defaults to verdict 'APPROVED' (pipeline-run.test.mjs scripted runners).
   This is the same works-in-fixtures/broken-live class as iteration-1 B1.
   Fix: append the verdict-tail instruction block to the writer prompt (one
   line, consistent with loop.mjs:360) and pin it — e.g. assert the writer
   prompt matches /End with exactly:\nVERDICT:/ in the seat-alternation or
   G3 tests.

2. MAJOR — pipeline failover is unbounded: infinite relaunch loop and
   unbounded spend under repeated limit/model deaths. drivePipeline has NO
   child-budget check (childSeq is incremented at pipeline.mjs:182 and never
   compared — the loop command's guard at loop.mjs:336 was not carried
   over), passes `avoid: [], avoidEntries: []` on every failover call
   (pipeline.mjs:287-288), and DISCARDS `decision.avoidEntries`
   (pipeline.mjs:293-295, contrast loop.mjs:420). Consequences: (a) two
   dead models on a chain ping-pong forever — each model-unavailable
   re-resolve starts from an empty avoidEntries and picks the other dead
   entry again; (b) alternating usage-limit deaths (A→B→A→B…) run full
   seal/receive transactions each cycle with no bound. Cost runaway is the
   plan's risk #3; relaunches deliberately bypass the gate cap, so the
   budget is the only bound — and it's absent. Fix: carry
   `decision.avoidEntries` into a per-subtask accumulator passed back into
   runFailover, and enforce a total child budget
   (maxChildrenPerPhase × subtasks, as loop run does) that parks on
   exhaustion; pin with a scripted always-limit runner.

3. MAJOR — the G4 orphan reap only exists under test injection: the real
   CLI io never defines processKill. acquireSupervisorLock kills recorded
   orphan groups only `if (typeof io.processKill === 'function')`
   (loop.mjs:175), the sole definition of processKill anywhere is the test
   double (loop-run.test.mjs:565), and core/bin/baton.mjs builds io with
   processAlive but NO processKill (verified by grep). In production a
   dead-lock reclaim therefore silently skips every kill AND then deletes
   children.ndjson (loop.mjs:181-185) — destroying the only record of the
   live orphans it just failed to reap. The "no orphaned children" recovery
   invariant currently holds only in fixtures. Fix: add
   `processKill: (pid, sig) => { try { process.kill(pid, sig); } catch {} }`
   to the bin io (and only unlink children.ndjson after the kill pass ran
   with a real killer available).

4. MAJOR — loop and pipeline share .handoff/loop/state.json with no
   flavor or spec binding, so cross-command resume misbehaves. Pipeline now
   loads whatever state exists (pipeline.mjs:149): state left by a `loop
   run` (e.g. phaseIndex 11 of a completed 11-phase loop) makes
   `for (i = state.phaseIndex; i < subtasks.length; …)` (pipeline.mjs:212)
   skip every subtask and report "done — N subtask(s) merged" with zero
   merges; a stale pipeline state against an EDITED subtask list indexes
   the wrong subtask; and PHASE_ADVANCE done-detection uses the OLD
   state.phaseCount, so a shorter subtask list can finish with status still
   'running'. Fix: stamp the persisted state with {flavor: 'loop'|'pipeline',
   specDigest} at init, and refuse (usage error naming the mismatch) or
   archive-and-reinit when the loaded state doesn't match the invoking
   command/spec; pin loop-state-then-pipeline-run.

5. minor — pid-reuse hazard in the reclaim killer: children.ndjson records
   are never pruned when a child completes normally (entries accumulate
   across runs; the file is only deleted on reclaim), and the kill decision
   is `io.processAlive(rec.pgid)` with the 1-arg form (loop.mjs:174) — no
   start-time cross-check, although bin's processAlive supports one. A
   recycled pid matching a stale record gets SIGKILLed as a group. Fix:
   remove (or tombstone) a child's record when superviseChild resolves, and
   record enough identity (startedAt vs process start time) to verify
   before killing.

6. minor — the first ESCALATION.md variant still says "Resolve the
   findings, then resume with baton loop run" (loop.mjs:331) even though an
   escalated run refuses both run (exit 3, loop.mjs:298-301) and resume
   (loop.mjs:260-263). The second variant (loop.mjs:471) carries no such
   instruction. B6's "correct the messages" was half-applied. Fix: reword
   the loop.mjs:331 template to the actual remediation (operator resolves
   findings, then clears/advances state deliberately — whatever the
   supported path is).

7. minor — crash window between mergeSubtask succeeding and the
   PHASE_ADVANCE transition (pipeline.mjs:359-364): a re-run resumes the
   same subtask, finds the branch merged (zero commits ahead of main), and
   parks with the misleading "produced an EMPTY branch" message
   (pipeline.mjs:313-314) instead of recognizing the landed merge. Fix: on
   an empty-ahead branch, check whether the branch tip is an ancestor of
   main and treat that as merge-complete → PHASE_ADVANCE, else park.

8. minor — the supervisor lock payload records runId `sup-${io.pid}`
   (loop.mjs:129), not the loop state's runId, so the refusal message
   ("run sup-12345") doesn't correlate with anything in state.json,
   journal, or ESCALATION.md. Fix: write the real runId after state load,
   or drop runId from the lock payload.

## Judgement for the v1 milestone gate

The fold is high quality where it landed: G1, G2, G5, G6, G7 are genuinely
closed with honest pins (the competitor-injection lock test and the
fail-closed read-only helper are particularly good), and the deferral
section makes G8–G14 auditable rather than silent. But finding 1 is the
same class that blocked iteration 1 — a one-line prompt omission that makes
the Layer-3 half of the milestone unable to complete any subtask outside
fixtures, discovered only because no test asserts the writer prompt's
contract. Findings 2 and 3 are real production holes in the newly added
failover/reclaim paths (unbounded spend; fixture-only orphan reaping).
These are cheap to fix and to pin; they are not cheap to ship.
