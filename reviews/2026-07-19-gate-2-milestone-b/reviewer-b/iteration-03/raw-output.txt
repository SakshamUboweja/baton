## NEW findings (fresh-eyes pass on the fold's own code)

1. MAJOR — the H7 auto-advance treats a stale EMPTY branch as already
   merged and silently skips the subtask. `git merge-base --is-ancestor
   <branch> main` (pipeline.mjs:239) succeeds whenever the branch tip is any
   ancestor of main — including a branch created by `checkout -b` whose
   writer never committed: its tip IS main's old HEAD. The vulnerable window
   is the entire pre-first-commit lifetime of a writer child (minutes, not
   milliseconds): supervisor dies after checkout but before the writer's
   first commit → resume prints "subtask '<id>' is already merged into main
   — advancing" (pipeline.mjs:245), no writer ever runs, and the pipeline
   completes reporting the subtask done. This replaces what was previously a
   correct natural resume (the seat is still on the branch, so the
   alreadyOnBranch path at pipeline.mjs:261-263 would have re-run the
   writer). Silent work loss in the recovery flow the fold was fixing.
   Fix: advance only when the branch actually contains subtask work — e.g.
   `git rev-list --count <seat-base>..<branch>` > 0 (tip differs from the
   seat's fork point) in addition to is-ancestor; or journal a
   subtask-merged event immediately after mergeSubtask succeeds and use the
   journal, not git inference, as the resume marker. Pin the negative: a
   pre-existing branch at main's tip with zero commits must NOT advance.

2. MAJOR — retire records mask genuinely in-flight children across
   invocations, re-opening the G4 orphan escape. childSeq resets to 0 every
   invocation and children.ndjson is never truncated on a normal (non-
   reclaim) lock acquisition, so a resumed run reuses childIds
   ('001-t1-writer', '001-plan') that a PREVIOUS invocation already retired.
   Reclaim matches starts to retires by childId alone (loop.mjs two-pass
   starts Map / retired Set): invocation 1 runs and retires 001-t1-writer;
   invocation 2 (resume after a park) starts 001-t1-writer again and the
   supervisor dies mid-child; invocation 3's reclaim finds childId
   001-t1-writer in the retired set and SKIPS the kill — the orphan writer
   survives, still mutating its seat worktree, while the new run spawns a
   second writer into the same seat. Resume-then-crash is exactly the
   scenario reclaim exists for.
   Fix: truncate children.ndjson on every successful lock acquisition (safe:
   a clean prior exit leaves only retired records; a dead prior owner's
   records were just processed by the reclaim pass) — or make childIds
   run-unique (runId + invocation nonce) and match retires per invocation.
   Pin: retire in run 1, same childId in-flight in run 2, dead lock →
   reclaim MUST kill.

3. minor — the loop-side H5 refusals leak the supervisor lock. In runLoop
   the flavor/specDigest mismatches `return usageError(...)`
   (loop.mjs:249-254) AFTER acquireSupervisorLock succeeded but BEFORE the
   try/finally that calls lock.release() — supervisor.lock stays behind.
   Self-heals via the dead-owner reclaim on the next run (noisy, and it
   needlessly runs the orphan pass), but with finding 5's 1-arg liveness
   check a recycled pid can wedge it into a permanent live-lock refusal.
   Pipeline is correct: its H5 refusals are inside runPipeline's try/finally
   (pipeline.mjs:118-124).
   Fix: perform the flavor/digest checks before acquiring the lock (they are
   read-only), or move them inside the released region.

4. minor — unstamped state bypasses the H5 binding entirely:
   `typeof state.flavor === 'string' && state.flavor !== …`
   (loop.mjs:249; pipeline.mjs:158) accepts any state.json with no flavor
   field, so state written by any pre-64e6cb5 run (or with the stamp
   stripped) still resumes under either command with the exact misalignment
   H5 exists to prevent.
   Fix: treat a missing stamp as a mismatch — refuse with the same archive
   instruction (v1 has no legacy-state population worth grandfathering).

5. minor — acquireSupervisorLock's liveness check calls
   `io.processAlive(other.pid)` with one argument (loop.mjs:161) even though
   the lock payload records startTime and bin's processAlive implements
   pid-reuse verification when given it — a recycled pid reads as a LIVE
   supervisor and refuses forever until the lock is hand-deleted.
   Fix: pass `other.startTime` as the second argument.

## Judgement for the v1 milestone gate

All eight iteration-2 dispositions are genuinely implemented and honestly
pinned — the fold quality is high, and the bin-io-shape pin is a
structurally good idea. But the two majors are not hygiene: both sit in the
crash/recovery path that acceptance constraint 4 promises ("recovers via the
journal and continues or parks, with no orphaned children"), and both were
introduced BY this fold — H7's recognizer silently skips unstarted subtasks
across a wide crash window, and H3's retire matching un-fixes G4's orphan
guarantee in the ordinary resume-then-crash sequence. Both fixes are small
and cheaply pinnable. Minors 3–5 can ride along in the same pass.
